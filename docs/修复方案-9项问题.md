## B1：进程生命周期重构（问题 2 + 5）—— 最高优先级

这是**所有问题的枢纽**：问题 1、2、5、7 全部收敛到「命令执行与会话解耦」这一件事上。不先做这个，后面都是补丁。

### B1.1 现状缺陷链

```
agent.ts:164   await consoleStore.attach(cmdId, command)   ← 阻塞到进程退出
console.ts:74-86  attach() 返回 Promise，等 console-exit 事件  ← Spring Boot 永不退出 → Promise 永不 resolve
console.ts:26  running getter 依赖 status === "running"       ← 状态是对的，只是没人把它接到 UI
agent.ts:269-272  stop() 里调 api.agentKillCommand(_cmdId)   ← 用户只能点停止，而停止 = 杀项目
agent.ts:61-63  _cmdId: 0  单值                             ← 多命令并发互相覆盖
```

结论：**不是 UI 没做状态，是 AI 会话把长驻进程 await 死了。**

### B1.2 改造方案

**Step 1｜Rust 侧新增「后台 spawn」语义**

`src-tauri/src/commands/agent.rs`：

1. `spawn_streaming`（`:541`）新增 `background: bool` 参数，并回传 `pid`。现有 `LIVE_PIDS: Mutex<Option<HashMap<u32,u32>>>`（`:54`）已有 pid，只是没暴露。
2. 新增 `pub(crate) fn spawn_detached(app, command, root, env) -> (u32, u32)`：`std::process::Command` 构好后 **立即 `spawn()` 并返回**，输出继续走 `console-output` / `console-exit` 事件泵（复用 `:572-593` 逻辑，不改）。
3. 新增 `#[tauri::command] agent_list_running() -> Vec<RunningProc>`：`{ cmd_id, pid, command, cwd, started_at, kind }`，供 UI 恢复与「重新打开工作区后仍知道有进程在跑」。
4. `kind` 字段是 B2 的关键：`SpawnKind::LongLived | SpawnKind::OneShot`，由调用方声明（配方/动作定义里带），不靠猜。

**Step 2｜消灭所有弹窗**

`agent.rs:549`：
```rust
Command::new("cmd").args(["/C", &command])
```
改为带 `CREATE_NO_WINDOW(0x08000000)`。建议封装到 `toolchain.rs:118 command_for()` 旁边做一个 `hidden(cmd: &mut Command) -> &mut Command` 工具，一次覆盖：

| 位置 | 内容 |
|---|---|
| `agent.rs:104` | `taskkill`（每次 kill 都弹一次） |
| `agent.rs:549` | 主犯，`cmd /C <command>` |
| `toolchain.rs:20-22` | `cmd /C where {name}`（每次探测 PATH 都弹） |
| `mcp/client.rs:36-44` | MCP server 启动 |
| `commands/os_open.rs:191` | — |

**同时修 dev 模式**：`main.rs:2` 现为
```rust
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]
```
dev 下要另起一个 `main` 包装，或在 dev 构建时也隐藏自身控制台，否则子进程仍可能继承。**验收标准：`npm run tauri dev` 下点启动，全程零黑窗。**

> 注意：`tauri.conf.json` 里**没有也不该有** `windows_subsystem` 字段（Tauri v2 只认 `main.rs` 的 `#![cfg_attr]`），不要往那儿加。

**Step 3｜`console.ts` 增加非阻塞 spawn**

```
console.ts 新增：
  spawn(command, opts): Promise<{ id, pid }>     // 立即返回，不等退出
  attach(id, command): Promise<RunResult>        // 保留，但仅供「一次性命令」用
  runningOf(actionKey): ConsoleRun | null        // 供 RunBar 查状态
  stop(id): void                                 // 转发 agentKillCommand
```
`ConsoleRun`（`console.ts:10-17`）扩两个字段：`action?: string`（关联 DevAction）、`pid?: number`。
`status` 从 `"running"|"done"|"failed"` 扩为 `"running"|"ready"|"done"|"failed"|"killed"` —— `ready` 表示「检测到 readyPattern，端口已监听」。

**Step 4｜`agent.ts` 解耦**

`agent.ts:153-168` 的 run_command 分支改为：

```ts
if (actionIsLongLived(key)) {          // run/start/serve/spring-boot:run
  const { id, pid } = await consoleStore.spawn(command, { action: key, background: true })
  obs = `[后台已启动] pid=${pid} cmd_id=${id}，输出持续写入控制台。`
  this.lastStarted = { id, pid, key }   // 不再 await 退出
} else {
  const { code, tail } = await consoleStore.attach(cmdId, command)
  obs = `exit=${code}\n${tail}`
}
```
循环随即继续，AI 正常收尾，`streaming` 归 false。**用户不再需要「断开」来解锁 UI。**

`agent.ts:269-272` 的 `stop()` 必须**删掉** `agentKillCommand` 这一行 —— 「停止 AI」与「杀进程」是两个语义。停止进程只在用户点 RunBar 的 ⏹ 时发生。

`_cmdId`（`agent.ts:61`）改为 `_cmdIds: Set<number>`。

**Step 5｜`recipe.ts:127` 对齐**

`runFast` 已经用 `void ... .then()` 实现了非阻塞（是好范例），但 B1.3 落地后应统一走 `consoleStore.spawn`，并让 AI 分支与配方分支共用同一条判定，避免两套行为。

## B6：JRebel 式热部署（问题 6）

**先说实话**：真 JRebel（字节码增强）不可能在轻量 IDE 里复刻。可行的是「**够用的替代方案**」，按成本从低到高分三档，建议先只做第 1 档验证需求强度。

### 档位 1｜Java 热重启（推荐先做，覆盖 80% 场景）

不是热替换，是「**自动重启**」，但对开发体验提升极大 —— 用户感受上接近热部署。

```
现有 notify watcher（code_index/engine.rs:172 update_file）
  + 变更分类器（pkg.rs 已有 ChangedKind 可借鉴）
  + 编译触发（复用 B4 的 maven 模块树！知道改的是哪个模块）

      ├─ 是 → 停旧进程（agent.rs:104 进程树杀）→ 重启（consoleStore.spawn）
      │        失败则**保持旧进程不动**，仅提示
      └─ 否 → 报编译错误，不动正在跑的进程
```
关键收益点：**依赖模块树（B4）+ 后台进程生命周期（B1）**都是前面批次已经建好的，B6 档位 1 主要是加一层 watcher 编排。

### 档位 2｜Java Agent 类加载增强（半热）

用 `java.lang.instrument` + 字节码织入做方法体替换（这是 JRebel 的原理）。要引入额外 JVM agent jar + Rust 侧 attach 能力。**工程量约等于再造半个项目**，且对 Spring AOP/事务/MyBatis 代理类失效。**建议明确不做**，除非用户有强诉求。

### 档位 3｜非 JVM 语言（性价比最高）

## B7：内置轻量本地模型（问题 9）

### B7.1 现状约束

`ToolchainPane.vue` 是**纯路径表单 + 探测**：`rows`（`:43-49`）5 行硬编码 jdk/maven/node/git/svn；`ToolInfo`（`toolchain.rs:7-16`）= `{kind, found, path, version, error}`，**装不下下载进度**（百分比/速度/已下载/目标目录）。`toolchain.rs` 只有 `.output()` 一次性调用，**无流式下载**。`config.rs:13-63` 的 `AppSettings` 无模型目录字段。

### B7.2 方案：三档本地能力（明确区分，避免过度承诺）

| 档位 | 方案 | 包体 | 用途 | 难度 |
|---|---|---|---|---|
| **A** | 内置分词器 + 启发式（**不做 AI**） | 0 | 本地代码联想、符号补全、TODO/未使用变量等静态提示 | 低 |
| **B** | 用户自带 Ollama / llama.cpp 服务端 | 0（只做连接配置） | 补全/问答走本地端点 | 低 |
| **C** | 应用内下载 GGUF 权重 + 内嵌推理 | 数百 MB | 开箱即用本地 AI | 高 |

**强烈建议先做 A + B**，把 C 作为可选的「模型下载」入口。A 档虽然不是 AI，但对「代码联想和快速解析」这个诉求 —— 复用**已有的 `code_index`**（`engine.rs:249` `search_symbols` 已做前缀/词边界/包含分级 + camelHump 分词 `:352`），把符号联想做成本地联想引擎，**零依赖零模型，效果立竿见影**。

### B7.3 B 档落地（推荐主推）

1. `config.rs:13-63` `AppSettings` 加 `local_llm_base`、`local_llm_model`、`local_llm_enabled`
2. `AiPane.vue:22-25`（现有 base/key/model 三个输入框旁）加「本地模型端点」分组
3. `agent.rs:367-506` `stream_chat_inner` 的 base 分派加一条 `LocalLlm` 分支（OpenAI 兼容协议，Ollama 直接兼容，**复用现有 SSE 解析代码**）
4. 探测命令：`ollama list` 探可用模型（复用 `toolchain.rs:236-284 detect` 的 match 范式，加 `local_llm` arm，否则会落到 `:282` 的 `"未知工具"` 分支）

### B7.4 C 档落地（若确实要做「设置里下载」）

数据结构不能塞进 `ToolInfo`，另起：
```rust
struct ModelDownload {
    model_id: String, name: String, size_bytes: u64,
    dest: PathBuf, state: DownloadState, downloaded: u64, speed: f64, error: Option<String>,
}
enum DownloadState { Idle | Downloading | Paused | Done | Failed }
```
- 新增 `#[tauri::command] model_download_start(model_id)`，用 `reqwest`（**已在 agent.rs:375 引入**）流式下载 + chunk 累加

- 下载目录存 **Tauri app 目录**（AGENTS.md：软件全局私有数据放 app 配置目录），持久化到 `config.rs`
- `ToolchainPane.vue` 加 `v-if="showModelPane"` 的独立分区（因为「路径表单 + 进度条」UI 形态完全不同，硬塞进 `rows` 数组会破坏现有组件抽象）
- 内存/磁盘告知：必须显示包体大小与磁盘占用提示，否则用户不知要下几个 G
- **GGUF 推理引擎建议用 `llama.cpp` 的 Rust 绑定而非内置**：绑定体积大且需 SIMD 变体；只做下载 + 走 Ollama 端点更稳
